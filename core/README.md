# hmgapi-hook

Feasibility test for HMG-API's hook runtime (Xposed-style method hooks on Dalvik 4.4), in three reversible steps:

1. **Wrapper** (done, EV6 US 2026-10-27): `zygote.c` is installed as `/system/bin/app_process` and runs the stock binary (`app_process.hmgapi-stock`) with the same arguments. It writes a `hmgapi-hook:` line to the kernel log on every pass. Stock ARM `app_process` re-execs itself once (`NO_ADDR_COMPAT_LAYOUT_FIXUP=1`), so the zygote passes through twice; only the first pass counts.
2. **Loader** (done, EV6 US 2026-10-27): `loader.c` → `libhmgapi_hook.so`, preloaded into the zygote (only with `/data/hmgapi/hook/enable`), so it is mapped in every app. For now it only logs `HMG-API: loaded in <pid>`. Boot guard: the wrapper counts zygote starts in `/data/hmgapi/hook/starts` and stops preloading at 3; a watcher it double-forks resets the count once that zygote has been up for 120 s. `/data/hmgapi/hook/disable` (`install/dev/hooks-off.sh`) turns it off without touching `/system`.
3. **Method hooks** (done, EV6 US 2026-10-27): `loader.c` interposes `JNI_CreateJavaVM`, swaps the zygote's `CallStaticVoidMethodV` once, and before `ZygoteInit.main` loads `/system/framework/hmgapi-hook.jar` (`java/`) and runs `Bridge.init()`. Hooks work like Xposed on Dalvik: the method becomes native, the original `Method` is kept as a copy. Java API shaped like Xposed (`MethodHook`, `Hooks.findAndHookMethod`). First hooks: `ActivityThread.handleBindApplication` (every app start) and, in the launcher, a log-only hook on `com.android.launcher3.view.a.g.load()`.
   - `install/dev/selftest.sh` runs `SelfTest` (12 checks: all argument types, results, skip, exceptions, constructors, 2 hooks, 2000 calls with GC) in a one-off `app_process`, away from the zygote.
   - The zygote unsets `LD_PRELOAD` once Dalvik is up (after the stock re-exec), so programs that apps start don't load the library.
   - **Launcher entry** (EV6 US 2026-10-27): after `a/g.load()`, HMG-API adds an `a/Q` entry for NEMESIS Manager with made-up resource ids (`0x7f7e0001`–`3`); in the launcher process, hooks on `Resources.getDrawable(int)`/`getText(int)` answer those ids with the activity's own icon and label (fallback: `sym_def_app_icon`, "HMG-API"). The launcher placed it as a new item in its first empty slot (index 18), and tapping it started `com.nemesis.manager/.MainActivity`.    - **Saved and movable** (EV6 US 2026-10-27): the first menu load after boot writes the entry into each profile's saved `menu_items` row (first "Empty view" slot, `itemId` 90; left alone once present). HomeSetting's editor gets the same hooks (`allmenuedit/z.load()` list + resources): it showed the entry, the owner moved it and saved, and the launcher kept the new position. With hooks off both apps drop it from what they show; the saved row keeps it until the editor saves again. 
4. **Mods** (EV6 US 2026-10-27): the zygote reads `/data/hmgapi/mods/<id>/` (`mod.json`, optional `settings.json` and `hooks.jar`, `.disabled` to turn one off). `provides.launcher` entries become menu items as above; `hooks` loads the mod's jar in the zygote (`DexClassLoader`, optimised into `/data/hmgapi/dalvik-cache`) and calls its `hmgapi.hook.ModEntry` (`zygoteInit`, `appLoaded`). Settings: defaults from `settings.json`, overridden by `/data/hmgapi/settings/<id>.json`. Saved menu items HMG-API adds use `itemId` 9000+; at each launcher start, one whose mod is gone becomes an empty slot again. Example mods: `nemesis-shortcut` (launcher entry only; now in its own repo, [hmgapi-nemesis-shortcut](https://github.com/Open-HMG/hmgapi-nemesis-shortcut)) and `mods/examples/hello` (code + a setting). `install/dev/mods-install.sh`, `install/dev/mods-remove.sh <id>`.
   - **★ keys** (EV6 US 2026-10-27): a mod's `provides.star_key` actions (`activity` or `broadcast`) become extra choices in the stock ★ lists: `CustomButtonSetting` (Nav/head-unit ★) and `CustomButtonSettingSWRC` (steering wheel ★). Before `initList()` HMG-API adds a `CustomItem(titleId, summaryId, iconId, "hmgapi.star.<mod>.<id>")` to `mMenuList`; after it, appends the rows with the screen's own `getListItem`, fixes the tick and refreshes the adapter; `initCustomKey()` (reset to default when no row matches) is skipped while the saved action belongs to an installed mod. Made-up ids `0x7f7d00xx` are answered by the resource hooks. The stock code saves the choice (`setKey`/`setCustomKey`); on a press ModeManagerService broadcasts it and HMG-API's receiver in the launcher runs it. At launcher start a key set to a removed mod's action goes back to "None"; `install/dev/keys-release.sh` (run by hooks-off and restore) does the same. Car results: "Open NEMESIS" showed in both lists, was saved for both keys, and each press opened NEMESIS Manager. Seen alongside: NEMESIS Manager's own close button crashes (`Ui.java:41` `finish()` → `SecurityException ... requires android.permission.GET_TASKS` on this head unit's activity manager); a NEMESIS issue, not HMG-API's.
   - **HMG-API's own entries** (EV6 US 2026-10-27): the app `hmgapi.app` (`core/app`, built without Gradle, own signing key in `~/hmg-private/keys/leafia-app.p12`) always gets a menu tile and an "Open HMG-API" ★ choice, listed before the mods' (mod id `hmgapi` is reserved); both only show while the app is installed. When the app starts, the hooks hand it the mod list (`hmgapi.app.HmgApiStatus.json`: id, name, version, state loaded/disabled/error, what it provides). First screen: hook runtime status and the installed mods. Car result: tile added to the saved menu (slot 18), app opened and listed both mods, "Open HMG-API" offered in both ★ lists.
   - Car results: both mods loaded; `hello` logged the owner's setting value in the zygote and the launcher; the existing NEMESIS item kept the owner's position (relabelled 9000); after `mods-remove.sh nemesis-shortcut` and a restart the launcher logged `removed … (its mod is gone), slot 18`, and the tile was gone from the menu and Edit menu. No crashes.

## Safety

- A broken `app_process` only stops the zygote. `adbd` (init class `core`) and the NEMESIS root daemon (`flash_recovery`) keep running, so `install/dev/restore.sh` works over ADB with Android down.
- adbd on these units never reads `ro.adb.secure` and has no `adb_keys`, so it doesn't check keys: ADB works whether Android is up or not.
- Run the unit scripts through the NEMESIS daemon: `adb shell /data/local/tmp/nemesis-d root -c '...'`, where `nemesis-d` is a non-SUID copy of `/system/xbin/nemesis`. Plain `nemesis root -c` from ADB runs locally with adbd's capability limit (CapEff `0xc0`): no remount, chown or `/data` writes. The scripts check this first and refuse.
- The stock `app_process` is backed up once to `/data/hmgapi/stock/system/bin/app_process`. Restore always uses that copy.
- Push with `adb push src/hmgapi-hook /data/local/tmp/` (into the parent): pushing into an existing `/data/local/tmp/hmgapi-hook` puts the new files one level down.
- The NEMESIS daemon runs commands with umask 0, so the scripts set `umask 077` and keep `/data/hmgapi` root-only; `restore.sh` refuses a backup whose md5 isn't stock (override: `HMGAPI_FORCE=1`).
- Tested on: steps 1 and 2 on a US EV6 (260507), 2026-10-27: zygote `hooks on, start 1`, library mapped in the zygote and its children, constructor logs, boot normal, `boot guard reset` at 122 s.
- Step 3 on the same car, 2026-10-27: self-test 12/12 PASS; zygote boot with the bridge: `bridge ready`, the app-start hook ran in 63 app processes, launcher hook logged `result true, 22 entries`, no crashes.
